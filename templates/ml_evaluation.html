This page is the argument for the model on the Fall Risk Ranking screen, laid out in the order the questions actually arise. It reads the saved artefact rather than refitting anything, so what you see below describes the model that is producing live scores right now.

Everything here is measured on synthetic data. The cohort was simulated from equations this project wrote, so the results show that the pipeline recovers a signal that was put there deliberately. That is internal validity. It is not evidence about falls in real care homes.

Act 1

Why is accuracy the wrong thing to ask about?

Falls are rare. Across {{ "{:,}".format(ds.n_samples) }} resident-weeks there were {{ ds.n_positive }} in which a fall followed — {{ (ds.positive_rate * 100) | round(1) }} % of them. A model that refuses to predict anything, and answers “no fall” every time for every resident, is therefore correct {{ (maj.accuracy * 100) | round(1) }} % of the time while catching none of the falls. Any accuracy figure quoted for this problem has to be read against that number, which is why it is not the number this page leads on.

What a high accuracy can hide

Four ways of setting the same model's alert threshold, plus the do-nothing predictor. Accuracy climbs as the threshold rises, purely by predicting the majority class more often.

The trap. At a threshold of 0.5 the model reaches {{ (results.operating_points.accuracy_matched_to_majority_baseline.accuracy * 100) | round(1) }} % accuracy — fractionally above the do-nothing predictor — and finds {{ (results.operating_points.accuracy_matched_to_majority_baseline.recall * 100) | round(1) }} % of falls. Reporting that accuracy without the recall beside it would be true and useless.

Act 2

Does it beat the paperwork the home already fills in?

“Better than chance” is a low bar and not the one that matters. Every home already records a falls-risk assessment score on paper, so the honest comparison is against that. Both baselines are shown below: the do-nothing predictor, and the existing paper score used directly as a ranking.

Ranking quality, unseen residents only

Act 3

How much of the score is the model cheating?

Consecutive 14-day windows from the same resident overlap and look alike. Shuffle rows at random into cross-validation folds and the model gets to learn what is normal for Mrs Brown, then is tested on Mrs Brown — and rewarded for the memorising. Splitting on residents instead removes that reward. Running both and reporting the difference turns the leak into a measurement.

Three ways of splitting the same data

Left to right, each split is stricter than the last. The distance between the first and last bar for a given model is that model's optimism gap.

A published fall-risk model that reported the row-shuffled figure alone would be reporting {{ results.leakage_analysis.row_shuffled_5fold_auc }} rather than {{ results.leakage_analysis.loso_auc }} — a difference this cohort happens to make small.

Act 5

Where should the alert threshold sit?

A ranking becomes a decision only when someone picks the line above which staff are told to act. Move it down and more falls are caught at the cost of more checks; move it up and the rota is quieter while more falls go unflagged. The threshold was chosen by maximising F2 on out-of-fold predictions — F2 weights recall four times as heavily as precision, because a missed fall costs an injury and a false alert costs a five-minute check. The asymmetry is a stated parameter, not a hidden default.

Act 6

When it says 40 %, does 40 % of the time a fall follow?

Ranking and probability are different claims. AUC only says the ordering is sensible; it is silent on whether the number printed next to a resident's name means anything. Class weighting, which is needed to get any recall at all on a {{ (ds.positive_rate * 100) | round(1) }} % positive problem, systematically inflates those numbers. An isotonic calibration layer fitted inside the cross-validation corrects them, and the correction is measured rather than assumed.

Predicted risk against what actually happened

Each point is a bin of predictions. The grey diagonal is perfect agreement: on it, a stated risk of 30 % means falls followed in 30 % of those weeks.

Act 7

What is it actually looking at — and why is that the catch?

Each feature is shuffled in turn and the drop in AUC recorded. A feature that matters loses the model a lot when scrambled; one that does not, costs nothing. This is the most useful chart on the page and the most dangerous one, for the reason set out underneath it.

Permutation importance — {{ results.feature_importance_model.replace('_',' ') }}

Mean drop in ROC-AUC when the feature is shuffled, averaged over five repeats.

The result recovers its own recipe

The generator couples fall hazard to a latent deterioration state, and drives fluid intake, wellbeing score and medication adherence from that same state. So the ordering above is, to a first approximation, the equations the data was written from, read back out.

This is a pipeline check, not a clinical finding. It shows that the feature engineering, windowing, causal cut-off and validation code can recover a temporal signal when one is present — which is worth demonstrating, and is all it demonstrates. Reading it as “fluid intake predicts falls” would be circular: fluid intake predicts falls here because this project wrote the line of code that made it so.
